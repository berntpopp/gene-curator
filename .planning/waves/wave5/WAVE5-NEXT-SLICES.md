## W5G — #435 PMID performance, review-entry locking and table/re-curation edges

**Start/ownership:** after A/B/D; owns publication_service.py, review_guards.py, crud/curation.py + workflow_engine.py review-entry orchestration, workflow endpoint bulk coordination, publication endpoint only if necessary; frontend usePmidLookup, EvidenceTableField, precurations store and CurationFormView link lookup; isolated tests. Coordinate with F if point-range guard imports change. No migration expected.

**Critical existing behavior:** /curations/{id}/submit -> submit_for_review -> claim_version locks row, then scoring/metadata mutation -> execute_transition -> _transition_to_review -> review_guards -> network. Generic /workflow/{type}/{id}/transition and /workflow/bulk-transition reach the same handler, which mutates stage/status before guard; the guard's queries can autoflush these writes and acquire the lock even without explicit FOR UPDATE. Moving the remote call a few lines within the handler is insufficient. Precuration review, approval/reject, peer-review routes need regression coverage but no new remote check unless they enter curation review.

**Smallest secure sequence, shared across all curation-to-review entry points:**
1. Read authorized item, expected lock_version, current status/stage and pinned evidence. Run local permission, transition and content/range checks before remote work. Capture the exact relevant state as plain immutable values, without dirtying ORM objects or claiming the row. Dedicated submit's caller-supplied version must still be checked.
2. Fetch/cache-check normalized PMIDs outside every row lock and before ORM writes. Local SELECT transaction is acceptable; do not indiscriminately rollback or commit someone else's transaction to release a lock. Prefer pure network lookup plus serial DB cache access; one SQLAlchemy Session/AsyncSession must not be used concurrently by tasks.
3. Obtain row lock or atomic version claim, forcibly refresh ORM state (identity-map cache is not a reread), verify expected version/evidence/status/pin still match and rerun local authorization/content checks. A changed item conflicts and stays unsubmitted; never use old lookup results for changed evidence, and never silently rebase submit to a newer version.
4. Only then set submission metadata, scores/stage and persist in the same transaction. Do not leave a second remote lookup under the lock. Move the dedicated submit's early claim/metadata into this shared ordering; avoid a public/client-controlled skip-validation flag. If internal preflight data is passed, bind it to exact item/version/evidence and reject mismatches.

**Bulk:** authorize/read eligible requested items first, normalize/deduplicate their PMIDs into one bounded remote preflight, then apply the same per-item state/version revalidation and existing partial-success semantics. Unknown PMIDs attach only to affected items. Do not parallelize writes on a shared session. Existing engine commits each successful transition, so transaction-local app.current_user_id must be restored for subsequent item work; do not add an admin RLS bypass. Failed item rollback must not poison later valid items.

**Timeout design:** browser batch size 10 alone cannot fix a 10s client timeout against a 15s per-request backend timeout. Existing submit `_fetch_all` already bounds concurrency at 5 and total time at 20s, but publication validate_pmids runs serially. Reuse bounded network fetching in the validation endpoint, keep cache reads/writes serial, and choose an explicit whole-batch deadline below client timeout with room for response overhead. Return per-PMID timeout/error for unfinished lookups, preserve completed definite not-found results, preserve order or map by PMID. Do not turn a timeout into not-found, leave loading forever, or lose a proven invalid PMID because another request timed out. Keep existing offline submission policy; report failures visibly and allow bounded retry/next blur.

**Frontend small edges:** checkAll must retry/report errored entries deliberately; disposal aborts work; watch [PMID list, disabled] so readonly→editable triggers validation even when rows unchanged; CSS.escape the column label in addRow focus selector. For re-curation, find approved precuration by gene+scope+approved filter from page zero or a targeted store action independent of current list pagination; distinguish pending/none correctly and preserve existing precuration link precedence. Do not fetch arbitrary giant page sizes.

**PostgreSQL concurrency regressions (real API as app_user, remote mocked):** use threading/events to pause the remote fetch deterministically, independent API sessions, and a short bounded wait rather than sleeps. While submit is paused, a second API save on the same curation must complete; when released, original submit conflicts, new evidence survives and status/score/pin are consistent. Parameterize dedicated submit, direct transition and bulk. Mutating the new saved PMID from known to unknown proves old preflight cannot authorize new evidence. Also pause then revoke accepted membership/change status; final permission/status checks reject. Two concurrent submits yield one transition/version increment, no double round/notification. An actual unknown PMID never commits; mixed known/unknown bulk preserves per-item result and app_user visibility after each commit.

**Other tests/browser:** timed-out individual plus already-known-not-found result; finite concurrency ceiling; duplicate PMID fetched once; cache hit no remote; response ordering; no concurrent session use; empty batch; readonly→editable/lazy tab/reload; quoted/bracketed column label focus; approved precuration outside current page. Browser narrow rechecks include actual Save click during outstanding PMID work and failed lookup retry. Tests never access Europe PMC network.

Delivery: failing tests, make check + make diff-cover + make ci, real PostgreSQL lane, independent Opus ponytail-review, merge.sh with pipefail, fresh isolated-stack monkey run and narrow fix rechecks. No frontend/backend scoring default change, no published snapshot correction, no new workflow bypass.

Not run: implementation tests or browser checks in this design-only assignment. Risks requiring reviewer attention: stale ORM state/autoflush and transaction-local RLS after bulk commits; timeout policy must preserve already-proven invalid PMIDs; #264 must not claim abandoned requirements completed.
